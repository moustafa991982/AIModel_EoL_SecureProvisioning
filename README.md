# CPYR on NVIDIA Jetson: secure boot, encryption at rest and remote attestation

**How an in-vehicle network anomaly detector ([CPYR](https://github.com/moustafa991982/Cpyr), SAE 2021-01-0196) is provisioned, booted, encrypted, measured and attested on a Jetson Orin-class platform — from fuse burning at the factory to signed analytics accepted by the fleet backend.**

Two deliverables:

1. **[Jetson Secure Provisioning Flow](https://moustafa991982.github.io/Cpyr-Jetson-SecureBoot-Attestation/)** (source: `docs/index.html`) — a single-page reference: a 40-step swimlane diagram of manufacturing (S1–S40), the field boot chain (B1–B11), and reference sections on fuses and FSKP, UEFI PK/KEK/db/dbx and `.auth` files, payload encryption, OP-TEE and the secure/normal world interface, LUKS with `luks-srv`, dm-verity, measured boot and PCR policy, the fTPM Endorsement and Attestation Keys, the quote path from Linux into OP-TEE, the `TPM_GENERATED_VALUE` magic number, AK–EK credential activation, the attestation session token and its `cnf` channel binding, and an **ISO/SAE 21434 TARA** of the attestation path.
2. **A runnable simulation** (`cpyr_secure_boot_demo.py`) of the same flow with real cryptography and real UEFI file formats, plus 14 attack scenarios that each show which control stops them.

> **Scope.** The cryptography, LUKS-style keyslots, dm-verity tree and UEFI `EFI_SIGNATURE_LIST` / `EFI_VARIABLE_AUTHENTICATION_2` files are real. NVIDIA components (BootROM, PSC, MB1/MB2, OP-TEE, fTPM, UEFI) are modelled in Python; key-derivation labels NVIDIA doesn't publish are marked `(sim)`. Nothing here is NVIDIA code or NVIDIA documentation. `ORIN_NOTES.md` covers what can be reproduced on a real (unfused) Orin dev kit.

## About the simulation

A runnable model of the [Jetson Secure Provisioning Flow](docs/index.html): how CPYR (in‑vehicle network anomaly detector, SAE 2021‑01‑0196) is provisioned, booted, attested and allowed to report on a Jetson Orin‑class device. Output tags match the page: steps **S1–S40** and boot stages **B1–B11**.


### Run it

```bash
pip install cryptography numpy               # torch only for --real-cpyr
python3 cpyr_secure_boot_demo.py             # manufacture one unit (S1–S40), then a field boot (B1–B11)
python3 cpyr_secure_boot_demo.py --list
python3 cpyr_secure_boot_demo.py --attack all
python3 cpyr_secure_boot_demo.py --export provisioning_package
python3 cpyr_secure_boot_demo.py --step       # pause between stages
```

To use the real CPYR model:
```bash
python3 train_cpyr_encoder.py --repo /path/to/Cpyr      # ~10 s on CPU → cpyr_artifacts/
python3 cpyr_secure_boot_demo.py --real-cpyr --attack all
```

`sample_output.txt` and `sample_output_real_cpyr.txt` contain full runs.

### What it models

| Phase / stage | In the script |
|---|---|
| S1 | PKC key (ECDSA P‑256), manufacturer CA, OEM_K1/K2 |
| S2–S4 | OEM RSA certificate → simulated NVIDIA wraps FSKP_AK/FSKP_EK with RSA‑OAEP → unwrapped in the "HSM" |
| S5 | Fuse blob: AES‑CTR with FSKP_EK, HMAC‑SHA256 with FSKP_AK (encrypt‑then‑MAC) |
| S6–S8 | UEFI PK/KEK/db as **RSA‑2048** keys, X.509 chain, real **EFI_SIGNATURE_LIST** and **EFI_VARIABLE_AUTHENTICATION_2 `.auth`** files (PKCS#7 over Name ‖ VendorGuid ‖ Attributes ‖ TimeStamp ‖ Data) |
| S9 | Boot chain BR‑BCT … UEFI signed with the PKC key |
| S10 | CPYR code partition (detector, manifest and, with `--real-cpyr`, the repo code) with a dm‑verity hash tree; root hash goes into the initrd |
| S11–S12 | Disk key into the EKB; CPYR data partition encrypted as a LUKS volume (random 512‑bit DEK, **AES‑256‑XTS per 4 KiB sector**), generic keyslot; inside it `model.bin.enc` (AES‑256‑GCM, CPYR model key) |
| S13 | Kernel and initrd encrypted with the payload key; boot entry signed with the **db** key |
| S14–S17 | Golden PCRs, EKB contents, backend, factory package |
| S18–S25 | Chip with a SKU ROM root key: BootROM re‑derives the FSKP keys, verifies the HMAC, decrypts, burns; read‑back; security‑mode fuse last |
| S26–S27 | `SetVariable(PK.auth, KEK.auth, db.auth)`: setup mode → user mode; per‑unit EKB = AES‑GCM under KDF(OEM_K1, ECID) |
| B1–B5 | PKC chain check → OP‑TEE opens the EKB → fTPM replays PCR0 → UEFI measures PCR7, checks db/dbx, PCR4, payload TA decrypts, SRV_DOWN |
| B6–B7 | `luks-srv`: generic passphrase on first boot, then re‑key: KDF(KDF(disk key, `luks-srv-ecid`, ECID), `luks-srv-passphrase-unique`, UUID); generic keyslot removed; SRV_DOWN; dm‑verity open |
| B9 | IMA → PCR10; `cpyr-ta` releases the model key only if the PCR policy matches; GCM + `weights_sha256` checks |
| B10 | Quote → AK → EK → CA, nonce, log replay, golden PCRs → **short‑lived session credential** |
| B11 / S38 | CPYR report signed by the PKCS#11 alert key, accepted only over a live attested session; end‑of‑line functional test (alerts only in the ATTACK phase); no generic keyslot left |

### Scenarios

| Scenario | Attack | Stopped by |
|---|---|---|
| `normal` | none: full manufacturing and a field boot | |
| `forged-fuse-blob` | rogue or bit‑flipped fuse blob | FSKP_AK HMAC in the BootROM |
| `disk-theft` | read the NVMe offline, leaked generic passphrase, move the disk to another unit | LUKS + per‑device passphrase |
| `tamper-model` | flip bytes in the LUKS ciphertext | XTS doesn't notice; GCM, IMA and the PCR policy do |
| `blind-detector` | patch the detector, rebuild the verity tree | root hash in the signed initrd |
| `tamper-initrd` | modify the encrypted initrd | db signature in UEFI |
| `db-inject` | self‑signed `db.auth` / `KEK.auth` | the authority chain |
| `auth-replay` | replay an old `db.auth`; retarget a KEK‑signed update to dbx | timestamp; variable name in the signed bytes |
| `downgrade` | boot the old, genuinely signed v1.0 | PCR policy and attestation; then an appended `dbx.auth` revokes it |
| `ta-closed` / `ta-left-open` | call the payload TA, `luks-srv` and `cpyr-ta` after boot | SRV_DOWN (CVE‑2026‑24153 pattern) |
| `replay-quote`, `forged-log` | attestation attacks | nonce; log replay |
| `unattested-analytics` | report without attesting, or with an expired credential | session credential |

### Export

`--export DIR` writes `oem_hsm/` (private keys, FSKP keys, fuse values, EKB plaintext and model plaintext, all **demo only**), `nvidia_exchange/oem_publickey.cer`, `certs/`, `uefi/*.esl` and `uefi/*.auth`, `factory_package/` (fuse blob, signed boot chain, boot entry, verity image and tree, LUKS data and header) and `backend/golden_pcrs.json`. The `.auth` files parse with OpenSSL: `openssl pkcs7 -inform DER -print_certs` on the CertData shows the signer.

### Simplifications

- The LUKS header is a JSON stand‑in using scrypt and AES‑GCM keyslots. Real LUKS2 uses argon2id and an AF‑splitter; the data encryption (AES‑XTS‑plain64 with a 512‑bit key) matches.
- The generic passphrase derivation, the FSKP derivation, the EKB key and the fTPM EK derivation labels are simulated.
- fTPM AK certification is a single EK signature, standing in for TPM2 MakeCredential/ActivateCredential.
- The stand‑in detector is not CPYR; use `--real-cpyr` for the repo's `conv_enocder`. Attack windows in real mode are synthetic payload fuzzing of real frames.

## Attestation in one paragraph

The fTPM (a trusted application inside OP-TEE) regenerates its **Endorsement Key** from a fuse-rooted seed; the OEM CA certifies it at the factory. The EK is decrypt-only, so an **Attestation Key** — a restricted signing key that never leaves the fTPM — is bound to it with `TPM2_MakeCredential` / `TPM2_ActivateCredential`. On every boot the backend sends a nonce, the AK signs a `TPMS_ATTEST` quote over PCR0/4/7/10 that starts with the magic `0xFF544347` (which a restricted key will never sign for external data), and the verifier checks the AK → EK → CA chain, the magic, the nonce, the event-log replay and the golden values. Only then does it issue a short-lived session token, bound with `cnf` to the device's mTLS key, that CPYR analytics must present. The TARA in the docs page rates 13 threat scenarios against this path.
