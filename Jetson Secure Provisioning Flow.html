Jetson Secure Provisioning Flow

From key generation in the OEM's HSM to a device that ships only after it proves, by fTPM attestation, that it booted the approved software. Secrets are decrypted only inside the HSM or inside the chip; the factory floor handles ciphertext and signed images, and the CPYR model stays encrypted at rest under a per-device LUKS key.

Phase 0

Preparation at the OEM secure site

Every key is created and used here, inside the OEM's HSM. What leaves this site is ciphertext, signatures and public keys.

  1. 1

    Generate root keys in the HSM

    OEM site

    Create the PKC bootloader-signing key pair (RSA-3K or ECDSA), the manufacturer CA that will certify each device's fTPM Endorsement Key, and the OEM_K1/K2 secrets that will be burned into fuses. Private keys are generated inside the HSM and never exported.

  2. 2

    Request FSKP keys from NVIDIA

    OEM site

    Through the NVIDIA representative, send one file: an X.509 certificate holding the OEM's RSA-4096 public key (oem_publickey.cer). Confirm its fingerprint with NVIDIA over a second channel so it cannot be swapped in transit.

  3. 3

    NVIDIA returns wrapped FSKP keys

    NVIDIA

    NVIDIA encrypts the FSKP keys to that certificate and returns Results.zip. For Orin: fskp_ak.bin.rsa_wrap and fskp_ek.bin.rsa_wrap plus per-OEM configuration strings. For Thor: a key-derivation key and a selection string.

  4. 4

    Unwrap the FSKP keys inside the HSM

    OEM site

    Decrypt the wrapped keys with the OEM's RSA private key. The plaintext FSKP keys can produce valid fuse blobs for every OEM device, so they stay inside the HSM.

  5. 5

    Build the fuse blob

    OEM site

    fskp_fuseburn.py turns the fuse configuration (OEM_K1/K2, PKC public-key hash, secure-boot and ODM settings) into a blob that is encrypted and authenticated with the FSKP keys. Only the chip's BootROM, which can re-derive those keys from its ROM, can open it.

  6. 6

    Generate the UEFI Secure Boot key pairs

    OEM site

    Create three key pairs in the HSM. PK (Platform Key) is the owner's root. KEK (Key Exchange Key) authorises changes to the signature databases. The db key signs the boot images UEFI will accept.

  7. 7

    Build the certificate chain PK → KEK → db

    OEM site

    PK self-signs its certificate and signs the KEK certificate. KEK signs the db certificate. The chain mirrors who may change what: PK controls KEK, KEK controls db and dbx.

  8. 8

    Build the signed UEFI variable updates

    OEM site

    Package each certificate list as an EFI_SIGNATURE_LIST and sign it as an authenticated .auth update. PK.auth is self-signed, KEK.auth is signed by PK, db.auth and dbx.auth are signed by KEK. Firmware accepts a write only if the signature chains to the level above.

  9. 9

    Sign NVIDIA's boot chain with the PKC key

    OEM site

    MB1, MB2, TOS (ATF + OP-TEE + trusted apps such as cpyr-ta and the fTPM) and the UEFI firmware are signed with the PKC private key. The BootROM checks them against the PKC hash in fuses. This chain sits below UEFI and is separate from PK/KEK/db.

  10. 10

    Build the rootfs and CPYR dm-verity image

    OEM site

    Build the root filesystem and the read-only CPYR partition (code, manifest, encrypted model), then run veritysetup format to produce the Merkle hash tree and its root hash. The root hash is written into the initrd. This must happen before the initrd is finalised and signed.

  11. 11

    Generate the disk-encryption key

    OEM site

    Generate disk_enc.key in the HSM and place it in the EKB. It is not the key that encrypts the data: on the device, OP-TEE's luks-srv trusted app uses it (through jetson_user_key_pta) to derive the LUKS passphrase, the key that unlocks a LUKS keyslot. The data itself is encrypted with a random master key (DEK) that cryptsetup generates and stores in the LUKS header, wrapped under that passphrase. disk_enc.key never appears in Linux.

  12. 12

    Build LUKS-encrypted images (dm-crypt)

    OEM site

    l4t_initrd_flash.sh with ROOTFS_ENC=1, -i disk_enc.key and --generic-passphrase encrypts the rootfs and the CPYR model/data partition as LUKS volumes (AES-XTS, 256-bit) and packages them for mass flashing (--massflash, --no-flash → mfi_<board>.tar.gz). One generic passphrase lets a single image be cloned to every unit. This is the at-rest protection for the model: a pulled NVMe or eMMC shows only ciphertext. dm-verity on the CPYR code partition still provides integrity, which AES-XTS alone does not.

  13. 13

    Encrypt and sign the boot entry

    OEM site

    Encrypt the kernel, initrd (carrying the verity root hash and CPYR loader) and DTB with the UEFI payload key, then sign the boot entry with the db private key. UEFI will boot it only if a db certificate verifies it and its hash is not in dbx. KEK and PK never sign images.

  14. 14

    Build the EKB

    OEM site

    Collect the UEFI payload key, the disk-encryption key, the CPYR model key, the alert-signing key and the sealed PCR policy into the Encrypted Key Blob. It is encrypted with a key derived from OEM_K1, so only OP-TEE on a device with those fuses can open it.

  15. 15

    Compute golden PCR values

    OEM site

    Replay the measurements this release will produce: PCR0 (boot chain), PCR4 (boot entry), PCR7 (PK/KEK/db/dbx) and PCR10 (IMA over the CPYR files). Their digest is the PCR policy sealed in the EKB.

  16. 16

    Store golden PCRs in the backend

    Backend

    The fleet verifier keeps the reference values per release. Attestation later compares each device's quoted PCRs against them.

  17. 17

    Release the factory package

    OEM site

    Hand over the encrypted fuse blob, the mfi package (signed boot chain, encrypted boot entry, LUKS-encrypted rootfs and CPYR partitions), the EKB and the .auth variable updates. No private key and no plaintext secret leaves the secure site.

Phase 1

Fuse burning on the factory floor

The factory station only relays an encrypted, authenticated blob. The chip decrypts it internally and writes the root of trust into one-time fuses.

  1. 18

    Factory receives the package

    Factory

    The station stores ciphertext, signatures and public keys only. Losing this package to an attacker reveals no secrets and cannot produce a device that boots attacker code.

  2. 19

    Put the board in Recovery (RCM) mode

    Factory

    Force-recovery over USB lets the host talk to the BootROM before any firmware is installed.

  3. 20

    Send the encrypted fuse blob

    Factory

    fskp_fuseburn.py transfers the blob to the chip. The host never sees the fuse values in plaintext.

  4. 21

    BootROM decrypts and authenticates the blob

    Device

    The BootROM re-derives the FSKP keys from its ROM root key and the per-OEM string, checks the blob is authentic, and decrypts it internally.

  5. 22

    Burn the root-of-trust fuses

    Device

    OEM_K1/K2, the PKC public-key hash and the secure-boot settings are written into one-time-programmable fuses. The UART log reports "Successfully burnt fuses as per fuse info".

  6. 23

    Fuses read back correctly?

    Device

    Verify the burned values before locking. Burning the security-mode fuse on top of a mistake can brick the unit or lock in a wrong key.

  7. 24

    Reject and quarantine the unit

    Factory

    A unit with bad fuses is scrapped or sent to failure analysis and logged, so it cannot re-enter the line.

  8. 25

    Burn the security-mode fuse last

    Device

    This locks the fuse configuration and disables debug access. From now on the BootROM boots only images signed with the OEM's PKC key.

Phase 2

Flashing

The signed and encrypted software and the UEFI key databases are written to storage. None of it is useful without keys the factory does not hold.

  1. 26

    Mass-flash the mfi package and enrol UEFI keys

    Factory

    l4t_initrd_flash.sh --flash-only --massflash writes the PKC-signed boot chain, the EKB partition, the PK/KEK/db/dbx .auth updates (enrolling PK moves UEFI from setup mode to user mode), the encrypted and signed boot entry, and the LUKS-encrypted rootfs and CPYR partitions (with the dm-verity hash tree for the CPYR code).

  2. 27

    Images stored on flash

    Device

    Everything on storage is signed, LUKS-encrypted, or integrity-protected by dm-verity. A storage dump reveals no keys and no model weights. At this point every unit still shares the generic disk passphrase.

Phase 3

First boot: per-device keys and identity enrolment

The device replaces the factory-wide disk key with one only it can derive, then gets a certified identity so the backend can trust its attestations for the rest of its life.

  1. 28

    First boot: unlock LUKS with the generic passphrase

    Device

    In the initrd, nvluks-srv-app asks the luks-srv trusted app in OP-TEE for the passphrase, and cryptsetup opens the volumes through dm-crypt. The kernel's tegra-crypto driver uses the SoC Security Engine, so data is decrypted block by block as it is read.

  2. 29

    Re-key: replace the generic passphrase with a per-device one

    Device

    luks-srv derives the per-device passphrase in two NIST SP 800-108 KDF steps inside OP-TEE: per-device LUKS key = KDF(EKB disk key, "luks-srv-ecid", chip ECID), then passphrase = KDF(per-device LUKS key, "luks-srv-passphrase-unique", disk UUID). The initrd's init script has cryptsetup add a keyslot that wraps the same master key (DEK) under this new passphrase and then remove the generic keyslot. Only the keyslot changes, so no data is re-encrypted. nvluks-srv-app then sends LUKS_SRV_TA_CMD_SRV_DOWN, so the passphrase cannot be requested again until reboot. A disk moved to another unit no longer opens, and the generic passphrase is useless once every unit is re-keyed.

  3. 30

    First boot: the fTPM derives its Endorsement Key

    Device

    The fTPM runs as a trusted application in OP-TEE and derives its EK from fuse secrets. The EK private key never leaves the secure world.

  4. 31

    Read the EK public key and ECID

    Factory

    The station collects the EK public key and the chip's ECID. Both are public identifiers.

  5. 32

    Manufacturer CA signs the EK certificate

    OEM site

    The HSM (online at the factory, or in a secure batch) issues an EK certificate. This certificate is what later lets the backend recognise a genuine device.

  6. 33

    Register the device in the backend

    Backend

    Store the ECID, the EK certificate and the public key that verifies CPYR alerts. Only enrolled devices are trusted later, which also limits factory overproduction.

Phase 4

End-of-line check

Each unit proves, before it ships, that it booted exactly the approved release.

  1. 34

    Backend sends a fresh nonce

    Backend

    A random challenge makes the quote fresh, so an old healthy quote cannot be replayed.

  2. 35

    Device boots and returns an fTPM quote

    Device

    The device boots normally, extending PCRs at every stage. The fTPM signs the selected PCRs plus the nonce with its Attestation Key and returns the quote, the event log and the AK certificate.

  3. 36

    Backend verifies the quote

    Backend

    Check that the AK chains to the EK and the EK chains to the manufacturer CA, that the signature and nonce are valid, that the event log replays to the quoted PCRs, and that the PCRs equal the golden values.

  4. 37

    Attested?

    Backend

    Every check above must pass.

  5. 38

    Quarantine the device

    Backend

    Mark it unenrolled so the fleet never trusts its data, and investigate the cause.

  6. 39

    Record in the manufacturing database

    Factory

    Log the fuse configuration, EK, release version and test results, and confirm the LUKS header holds no generic keyslot. This record supports audits, RMA and revocation.

  7. 40

    Ship the device

    Factory

    The unit leaves the factory locked, enrolled and proven to run the approved release.

UEFI Secure Boot keys and .auth updates

PK, KEK and db are three key pairs with three different jobs. Only the db signing key ever signs a boot image.

Private keySignsFirmware verifies againstTypical custody

KEKdb.auth, dbx.authcertificates in KEKHSM, rare use

Formats. A .pem/.crt holds a key or certificate. An .esl (EFI_SIGNATURE_LIST) holds certificates or SHA-256 hashes, each tagged with a SignatureOwner GUID. An .auth is a signed request to change one variable: EFI_VARIABLE_AUTHENTICATION_2 (timestamp + PKCS#7 signature) followed by the ESL.

cert-to-efi-sig-list -g <owner-guid> db.crt db.esl            # PEM → ESL
sign-efi-sig-list -k KEK.key -c KEK.crt db db.esl db.auth     # ESL → signed .auth
sign-efi-sig-list -a -k KEK.key -c KEK.crt dbx rev.esl dbx.auth   # append a revocation

Setup vs user mode. With no PK enrolled the firmware is in setup mode and accepts a self-signed PK.auth; enrolling it switches to user mode, after which every write needs a valid .auth. Attributes are NV | BS | RT | TIME_BASED_AUTHENTICATED_WRITE_ACCESS (0x27); adding APPEND_WRITE (0x40) appends instead of replacing, which is how dbx revocations are pushed in the field over OTA.

UEFI payload encryption

Why quotes are not signed with the EK.

ReasonDetail
The TPM refusesthe EK has no sign attribute, so TPM2_Quote / TPM2_Sign reject it before any crypto runs; using it also needs endorsement-hierarchy authorization
Key separationwith RSA, decrypt and sign are the same private operation; one key doing both invites cross-protocol attacks (a decryption request that is really a signature)

Limit. The fTPM is only as strong as OP-TEE and TrustZone: a secure-world exploit can forge quotes. NVIDIA's fTPM provisioning needs a fused, secure-boot-enabled unit, so attestation on an unfused dev kit proves nothing.

Why the factory never sees a secret

The fuse blob is encrypted with an FSKP key that exists only in the HSM and in the SoC's ROM. The BootROM decrypts it internally while burning fuses.

Model encrypted at rest

The CPYR model sits on a LUKS (dm-crypt) volume whose key luks-srv derives inside OP-TEE from the EKB disk key and the chip's ECID. The PCR-gated model key adds a second layer on top.

UEFI Secure Boot keys

PK signs KEK; KEK signs db and dbx updates; the db key signs the boot entry (kernel, initrd, DTB). The rootfs is not signed by UEFI: its dm-verity root hash rides inside the signed initrd.

Why the security-mode fuse goes last

Once burned it locks the configuration and disables debug. Reading back the other fuses first avoids locking in a mistake.

Why the device must attest before shipping

The backend checks the quote's AK → EK → CA chain, the nonce, the event log and the golden PCRs, so each unit proves it booted this exact release.
